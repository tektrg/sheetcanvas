ClickHouse tutorial

Build a ClickHouse query dashboard canvas.

Use SheetCanvas to run a focused read-only ClickHouse query through the backend connector, import the result as a connected sheet, and keep the table beside charts, pivots, sparklines, and notes. This walkthrough is for repeated review questions where the result needs visible context, not for database administration.

Query setup

Start with one read-only question.

The ClickHouse connector is strongest when a query returns a focused result set that can be refreshed and explained on the canvas. Keep administration, schema changes, and exploratory SQL editing in your database tools.

1. Use the backend connector

Save the ClickHouse HTTP URL and credentials through the SheetCanvas connector flow so the browser does not connect to the database directly.

2. Keep SQL read-only

Use one SELECT or WITH statement. The backend rejects write-style operations and multi-statement SQL.

3. Import a bounded table

Return the columns needed for the review, then let SheetCanvas place the rows as a connected sheet that can be refreshed later.

Prerequisites

Prepare the connector before designing the canvas.

A useful ClickHouse canvas starts with a safe connection and a narrow reporting question. Do this setup once, then use the canvas for analysis and review.

  • Backend worker: the SheetCanvas frontend sends connector requests to the backend proxy. The browser should not hold the ClickHouse password or call the database directly.
  • Read-only account: use a ClickHouse user intended for analysis reads. The SheetCanvas connector still validates query shape, but the database account should also be scoped to the data you are comfortable reviewing.
  • Focused source table: choose the event, order, account, or operations table that answers the current review question. Avoid importing a broad warehouse extract just because it is available.
  • Expected row count: start with a bounded date range, segment, or LIMIT. The backend caps returned rows and can mark truncated results, so the first version of the query should already be canvas-sized.
  • Review owner: decide who will read the canvas. A founder reviewing growth, an operator checking latency, and an analyst reviewing revenue need different columns and chart objects.

SQL shape

Write the query like a dashboard source, not a scratchpad.

SheetCanvas expects a single read-only statement. A good first query returns plain columns that can be charted, pivoted, and discussed without extra cleanup.

Use column aliases that will make sense on the canvas. A result with event_day, source, sessions, and conversion_rate is easier to turn into chart and pivot objects than a result full of temporary expression names.

SELECT
  toDate(event_time) AS event_day,
  traffic_source AS source,
  count() AS sessions,
  uniqExact(user_id) AS users,
  sumIf(1, event_name = 'signup') AS signups
FROM product_events
WHERE event_time >= now() - INTERVAL 30 DAY
GROUP BY event_day, source
ORDER BY event_day DESC, sessions DESC
LIMIT 500

This is only an example shape. The important parts are the constraints: one statement, read-only SQL, analysis-ready columns, and a row count small enough to keep the canvas readable. If you need several unrelated questions, create separate connected sheets so each table has a clear purpose.

Canvas workflow

Build the review around the query result.

The useful pattern is to keep the source query result and the interpretation together. That makes it easier to see which chart, pivot, note, or follow-up question came from which rows.

  • Anchor the connected sheet: place the ClickHouse result near the upper-left of the canvas so it remains the source of truth.
  • Chart one question at a time: use separate chart objects for volume, conversion, latency, revenue, or segment mix instead of one crowded dashboard.
  • Use pivots for segment review: group by campaign, account, source, product, region, or event class when the query returns analysis-ready columns.
  • Add notes beside outliers: keep caveats, assumptions, and follow-up SQL ideas next to the exact chart or pivot that raised the question.

Layout

Arrange the canvas by decision flow.

A ClickHouse result often starts as a database answer, but the canvas should turn it into a review path. Put the raw table, visual summaries, and interpretation in an order a teammate can scan.

Source zone

Keep the connected sheet visible and label it with the question it answers, such as "30-day acquisition by source" or "weekly error volume by endpoint". When someone asks where a chart came from, the source rows are still on the canvas.

Visual zone

Create charts, pivots, or sparklines that each answer one follow-up. Use small objects with clear labels instead of a dense dashboard that hides the query assumptions.

Decision zone

Use notes for interpretation, next actions, and caveats. If a number looks wrong, write the follow-up query idea beside the chart instead of losing it in a separate document.

Result handling

Keep the connected sheet traceable.

After a successful query, SheetCanvas stores connector metadata on the sheet so the table can be refreshed later. Treat that sheet as the source object for every visual built from it.

  • Preserve the query purpose: name the sheet after the business or product question, not just the ClickHouse table name.
  • Watch truncation state: if the backend marks the result as truncated, narrow the query before making decisions from the tail of the result set.
  • Keep derived objects nearby: place charts, pivots, and sparklines close enough to the connected sheet that their source stays obvious.
  • Separate experiments: when you need a second SQL variant, create another connected sheet rather than overwriting the first review surface.

Review checklist

Check the canvas before sharing it.

The final review is less about decoration and more about whether a teammate can understand the data source, the visual summary, and the decision without opening a separate SQL notebook.

  • Can someone find the source? The connected sheet should still be visible, named clearly, and close to the charts or pivots that depend on it.
  • Can someone see the time window? If the date range is part of the query, put it in the sheet name or a nearby note so a refreshed canvas is not misread as all-time data.
  • Can someone see what changed? If you refresh the sheet before a meeting, add a short note about the refresh time and any visible difference that matters for the decision.
  • Can someone trust the limits? If rows were truncated or filtered heavily, note that beside the source table before using the visuals as a final answer.
  • Can someone act on it? Put the follow-up owner, next SQL idea, or product decision near the relevant object so the canvas remains a working surface rather than a static screenshot.

Boundaries

Use the right tool for the parts around the canvas.

SheetCanvas is useful once a query result is ready to review visually. It does not need to replace ClickHouse administration, SQL development, access management, or deeper BI governance.

Keep database work in ClickHouse tools

Use your normal database tooling for schema design, permissions, performance tuning, migrations, and broad exploratory SQL work. Bring the result into SheetCanvas when it is ready for visual review.

Keep governed dashboards in BI tools

If a metric needs company-wide definitions, scheduled distribution, permissions, or production dashboard governance, keep that in the system your team already uses for formal reporting.

Use SheetCanvas for working analysis

Use the canvas when the question is still being discussed and the source table, visuals, caveats, and notes need to stay together while the team decides what to do next.

Refresh and limits

Refresh the same question, not every possible query.

SheetCanvas stores connector metadata and refresh state on the connected sheet. If the question changes, create a separate connected sheet with a separate SQL query so the canvas remains readable and the source for each visual stays clear. A refresh should update the same review question, not silently turn the canvas into a different report.

If a refresh fails, check backend availability, connector credentials, SQL shape, row limits, and ClickHouse HTTP access before rearranging the canvas. Failed refreshes should be treated as source-data problems first, because the chart or pivot objects are only as useful as the connected table they depend on.
